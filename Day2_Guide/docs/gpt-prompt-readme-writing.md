# GPT에 보낼 질문지 — Ansible 패턴 README 작성 지침 요청

> 이 파일은 GPT(또는 다른 LLM)에 그대로 복사해 붙여넣어 "사람이 이해할 수 있는 한국어 README 작성 지침"을 받기 위한 프롬프트다.
> "여기서부터" 줄 아래 전체를 복사하면 된다.

---

## 여기서부터 복사

당신은 **한국어 기술 문서 작성 코치**이자 **Ansible 교육 콘텐츠 시니어 편집자**다.
나는 사내 인프라 자동화 학습용 GitHub 리포지토리(`Infrastructure-Automation-Project`)를 운영 중이고,
그 안에 `playbook/patterns/` 라는 디렉토리를 두고 **Ansible 문법·구조 패턴 12종**(roles, block-rescue, tags, handlers, conditionals, loops, templates, assert-fail, register-when, import-include, lookup, delegate-runonce)을
각 디렉토리별 **`site.yml` + `README.md`** 쌍으로 데모하고 있다.

문제는 내가 AI에게 부탁해서 받은 한글 README가 **읽는 사람이 무슨 말인지 모르겠다**는 피드백을 계속 받는다는 점이다.
당신에게 부탁할 것은 "잘 쓴 예시 한 편"이 아니라, **앞으로 내가 12개 README를 같은 톤으로 다시 쓸 수 있는 작성 지침서(스타일 가이드)** 다.

---

### 1. 독자 정의를 먼저 잡아달라

다음 조건을 만족하는 "표준 독자 페르소나"를 1~2개 만들어 달라.

- 리눅스(RHEL 9 위주) **운영 경험은 있지만** Ansible은 처음 만지는 인프라 담당자
- YAML, SSH, systemd, dnf 정도는 알지만 **Jinja2/멱등성/fact/handler/register 같은 Ansible 특화 용어는 모른다**
- 회사에서 "Jenkins → Ansible로 작업을 옮긴다"는 흐름에 끌려온 사람이 많다

페르소나 정의에는 **그 사람이 이 문서를 언제·왜 열어보는지**(예: 운영 중에 막혀서, 교육 시간에, 학습 차원에서)까지 포함시켜 달라.

---

### 2. 패턴 README의 표준 구조를 제시해 달라

12개 README 모두에 적용 가능한 **고정 섹션 순서**를 추천해 달라. 각 섹션마다 다음을 알려달라.

- 섹션 제목(한국어, 한 줄 요약 포함)
- 그 섹션에서 **반드시 답해야 하는 질문**(예: "왜 이게 필요한가?", "안 쓰면 뭐가 불편한가?")
- 권장 분량(문장 수 또는 줄 수)
- 들어가면 안 되는 것(예: 너무 이른 고급 옵션, 다른 패턴과의 비교 등)

내가 지금 쓰고 있는 섹션은 대략 이 정도다 — 더하거나 빼거나 순서를 바꿔도 좋다.

1. 한 줄 요약
2. 왜 필요한가 (실무 시나리오)
3. 동작 흐름 (코드 예시)
4. 직접 돌려보기 (실행 커맨드 + 기대 결과)
5. 자주 쓰는 모양 (표)
6. 실제 작업에서 어디 쓰이나 (이 리포 내 다른 디렉토리 참조)

---

### 3. "왜 필요한가"를 잘 쓰는 법

기술 문서에서 가장 자주 무너지는 부분이 도입부다.
초보자에게 "이 기능이 왜 존재하는가"를 **3~5문장 안에** 와 닿게 설명하는 방법을 알려달라.

가능하면 다음 도구들을 언제 써야 하고 언제 피해야 하는지도 같이 말해달라.

- 비유(예: handler를 "건드린 사람만 신경 쓰는 매니저"로 비유)
- Before/After 시나리오(이 패턴 없이 짜면 vs. 쓰면)
- 실패 사례·장애 회고형 도입
- 숫자(몇 대 서버, 몇 분 단축 등)

---

### 4. 코드 예시를 "읽히게" 하는 법

YAML 블록만 던지면 독자가 못 읽는다. 다음을 결정해달라.

- 코드 예시는 한 README당 몇 개가 적정인가
- 코드 위/아래/옆 중 어디에 설명을 붙이는 게 좋은가
- 인라인 주석(`# ...`) vs. 별도 본문 해설 중 어떤 게 한국어 학습 자료에 더 맞는가
- "전체 site.yml을 그대로 보여줄지" vs. "핵심 줄만 잘라서 보여줄지"의 기준
- 출력 예시(`PLAY RECAP`, `changed=1` 등)를 같이 보여줄 때의 포맷

---

### 5. 한국어 문장 스타일 가이드

내 기존 README에서 자주 지적받는 패턴이 있다. 다음에 대해 명확한 규칙을 정해달라.

- 종결어미: 평어체("~한다") vs. 해요체("~해요") vs. 명사형("~함") — 교육용에는 무엇이 적합한가
- 영어 용어 처리: `handler`를 "핸들러"로 적는가, 원어 그대로 두는가, 첫 등장 시 괄호로 병기하는가
- 번역투("~에 대해", "~을(를) 가지는") 줄이는 체크리스트
- 한 문장 길이 상한, 한 문단 줄 수 상한
- 백틱(` ` ``  ` `)·**굵게**·이탤릭의 사용 기준
- 표 vs. 리스트 vs. 문단의 선택 기준

---

### 6. Ansible 특화 개념을 처음 만나는 사람에게 설명하는 법

다음 개념들이 README 전체에서 반복적으로 등장한다.
각각을 **딱 한 문장으로** 처음 등장 시 어떻게 한 번 설명하고 넘어가야 하는지, 그 한 문장 템플릿을 만들어달라.

- 멱등성(idempotency)
- fact / `gather_facts`
- handler / notify
- register / when
- play / playbook / task / role
- inventory / group_vars / host_vars
- delegate_to / run_once
- block / rescue / always
- check mode / diff mode
- become / privilege escalation

---

### 7. "직접 돌려보기" 섹션을 신뢰감 있게 쓰는 법

학습자가 그대로 따라 했을 때 막히지 않도록 다음을 정해달라.

- 실행 전 전제 조건(인벤토리 위치, 권한, OS 등) 어디에 어떤 형식으로 명시
- 명령어 한 줄과 함께 보여줄 "기대 결과"의 분량
- 같은 명령을 두 번째 돌렸을 때(멱등성 확인) 어떤 차이를 강조해서 보여줄지
- 실패했을 때 사용자가 자가진단할 수 있는 미니 트러블슈팅 박스 양식

---

### 8. 12개 패턴 사이의 일관성

12개 README가 각자 다른 사람 손에 쓰인 듯한 느낌을 없애려 한다.

- 디렉토리 간 상호 참조(예: "block-rescue를 이해하려면 먼저 register-when을 보라")를 README에 어떻게 녹일지
- 메인 `patterns/README.md` 의 학습 순서와 각 README 도입부를 어떻게 연결할지
- 패턴별 난이도 표기(★☆☆ 식) 도입이 도움이 될지, 오히려 부담을 줄지

### 10. 산출물 형식 요청

위 1~9의 답을 다음 형식으로 정리해서 줘.

1. 먼저 **표준 독자 페르소나** (1~2명)
2. 그 다음 **README 표준 템플릿**(섹션별 빈 양식 + 각 섹션 작성 규칙)
3. 그 다음 **한국어 스타일 가이드 체크리스트** (15~20개 항목, 체크박스 형태)
4. 그 다음 **Ansible 용어 한 문장 사전** (10개 내외)
5. 마지막으로 **샘플 변환**: 아래의 "현재 내가 쓴 conditionals/README.md"를 위 가이드에 맞춰 다시 써준 버전 한 편을 보여달라.

전체 길이는 너무 압축하지 말고, 내가 12개를 같은 톤으로 다시 쓸 때 참고할 수 있을 만큼 충분히 풀어서 써달라.

### 11. 참고용 — 내가 현재 쓰고 있는 README 한 편 (`patterns/conditionals/README.md`)

````markdown
# patterns/conditionals — 호스트나 상황에 따라 다르게 실행

같은 task 라도 호스트마다 다르게 동작해야 할 때가 있다:

- RHEL 에선 `dnf`, Ubuntu 에선 `apt` 로 패키지 설치 (패키지 매니저가 다름)
- 메모리 큰 서버에만 빠른 모드 활성화
- prod 환경에서만 슬랙 알림 보내기

task 옆에 `when:` 키워드를 붙이면 "**이 조건이 참일 때만 실행**" 이 된다. 조건이 거짓이면 그 task 는 그냥 skip (안 돌고 넘어감).

## 동작 흐름

```yaml
- name: RedHat 계열에서만 실행
  ansible.builtin.debug:
    msg: "RHEL 계열입니다"
  when: ansible_facts.os_family == 'RedHat'
```

`gather_facts: true` 가 필수다. 호스트 정보(OS, 메모리, CPU 등) 를 미리 수집해야 조건을 평가할 수 있다.

## 직접 돌려보기

```bash
ansible-playbook -i 인벤토리 site.yml
```

호스트 종류에 따라 어떤 task 는 실행되고 어떤 건 `skipping` 으로 표시된다. RHEL 9 호스트에서 돌리면 "RHEL 9 x86_64 환경" task 까지 다 통과한다.

## `when:` 의 흔한 모양

| 쓰임             | 예시                                              |
|:-----------------|:--------------------------------------------------|
| 단일 조건        | `when: 변수 == 값`                                |
| AND 여러 조건    | `when:` 아래 리스트로 — 모두 참이어야 실행        |
| OR               | `when: 조건A or 조건B`                            |
| 부정             | `when: not 조건`, `when: 값 not in [...]`         |
| 변수가 정의됐는지 | `when: my_var is defined`                         |

## 실제 작업에서 어디 쓰이나

- `tasks/linux/pkg-update/` — `os_family == 'RedHat'` / `== 'Debian'` 으로 dnf/apt 분기
- `sandbox/` 의 `pre.yml` — RHEL 9 인지 확인하고 통과한 호스트만 다음 단계로
````

이 글이 **왜 어렵게 느껴지는지** 진단부터 한 뒤, 위 10번 산출물 형식으로 본격적인 가이드를 작성해달라.

### 12. 추가 제약

- 우리 환경은 **Linux(RHEL 9) 전용**이다. Windows/macOS/네트워크 장비용 분기는 다루지 않는다. 예시도 Linux 한정으로 유지해달라.
- Ansible은 **2.15 이상**을 가정한다. (`ansible.builtin.*` FQCN 사용)
- 학습자는 **Jenkins → Ansible 전환** 흐름에 있으므로, 가능하면 Jenkins 비교가 자연스러운 곳에는 짧게 곁들여도 좋다(단, 모든 패턴에 무리하게 끼워넣지는 말 것).
